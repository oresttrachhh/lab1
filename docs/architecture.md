# Архітектура Build Engineer Agent

## Призначення та проблеми, які вирішує агент

Build Engineer Agent — це спеціалізований агент для підготовки Java-проєктів до
розробки та безперервної інтеграції. Він вирішує такі проблеми:

- ручне й непослідовне створення структури Maven-проєкту;
- помилки в `pom.xml` та налаштуванні JUnit 5;
- відсутність стандартного процесу складання і запуску тестів;
- ручне створення або неповна конфігурація GitHub Actions;
- складність первинної перевірки готовності репозиторію.

Демонстраційний результат роботи агента — проєкт **HelloProject** на Java з
Maven, JUnit 5 і CI workflow для GitHub Actions.

## Skills агента

Агент використовує такі Skills:

### `project-scaffold`

Створює або перевіряє стандартну структуру Java-проєкту, зокрема каталоги
`src/main/java` і `src/test/java`, базові класи та початкові файли конфігурації.

### `build-and-test`

Налаштовує Maven, JUnit 5 та плагіни, запускає складання і тести, а також
аналізує помилки компіляції чи тестування.

### `github-actions`

Створює CI workflow для GitHub Actions, який встановлює потрібну версію Java,
виконує Maven build і запускає тести.

## Доступні команди

- **`git-init`** — ініціалізація Git і перевірка кореня репозиторію.
- **`create-project`** — створення структури HelloProject.
- **`create-build`** — створення або оновлення Maven build-конфігурації та
  налаштування JUnit 5.
- **`create-actions`** — створення GitHub Actions workflow.
- **`check`** — перевірка структури, конфігурації, складання і тестів.
- **`init`** — оркестрація повного сценарію: `git-init`,
  `create-project`, `create-build`, `create-actions`, `check`.

## Дані між етапами

Етапи передають один одному структурований контекст виконання:

- кореневий шлях репозиторію;
- назву проєкту та координати Maven (`groupId`, `artifactId`, `version`);
- обрані версії Java, Maven і JUnit 5;
- список створених або змінених файлів;
- результати перевірок і команди, які були виконані;
- перелік помилок, попереджень і невирішених залежностей.

Наступний етап використовує лише підтверджені результати попереднього етапу.
Фактичний стан файлової системи та Git перевіряється перед змінами, тому агент
не покладається тільки на текстовий контекст.

## Оркестрація виконання

Оркестратор розбирає команду користувача, визначає потрібний Skill і перевіряє
передумови. Для `init` етапи виконуються послідовно, оскільки кожен наступний
етап використовує результати попереднього:

1. `git-init` перевіряє або ініціалізує Git.
2. `create-project` готує структуру Java-проєкту.
3. `create-build` додає Maven і JUnit 5.
4. `create-actions` додає CI workflow.
5. `check` виконує фінальну перевірку.

Незалежні операції можуть бути об'єднані лише тоді, коли вони не змінюють один
і той самий файл і не залежать від результату іншої операції. Після кожного
етапу оркестратор фіксує результат і зупиняє залежні кроки, якщо передумова не
виконана.

## Обробка помилок і конфігурації

Агент явно повідомляє про помилки із зазначенням команди, файлу або залежності,
що спричинили проблему. Він:

- перевіряє наявність Java, Maven і Git до запуску відповідних команд;
- не приховує помилки компіляції, тестів або GitHub Actions;
- розрізняє відсутній інструмент, відсутню залежність, помилку конфігурації та
  помилку виконання;
- не продовжує залежні етапи після невдалого критичного кроку;
- для некоректного `pom.xml` або workflow показує конкретний фрагмент і
  пропонує виправлення;
- повторно перевіряє результат після виправлення.

Якщо потрібна залежність недоступна через мережу або Maven-репозиторій, агент
повідомляє про це як про блокуючу проблему й не створює успішний результат
замість невдалого складання.

## Ідемпотентність і безпечний повторний запуск

Команди можна безпечно запускати повторно. Перед змінами агент:

- перевіряє, чи існують потрібні каталоги та файли;
- порівнює наявну конфігурацію з очікуваною;
- не дублює залежності, plugin-и або workflow;
- оновлює лише необхідні секції та зберігає несуміжні користувацькі зміни;
- не видаляє файли без явної потреби та підтвердження;
- після виконання запускає цільову перевірку.

Таким чином, повторний виклик `init` приводить проєкт до того самого
очікуваного стану, не створюючи дублікати й не руйнуючи вже коректну
конфігурацію.
