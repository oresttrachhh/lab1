# Журнал використання GitHub Copilot Agent

Цей журнал узагальнює факти, які можна підтвердити файлами проєкту, історією
Git, історією GitHub Actions і доступними назвами сесій Agent. Дослівні тексти
запитів, відповідей AI та всіх повідомлень про помилки не збереглися, тому
нижче наведено короткий зміст; неповні відомості позначено прямо.

## 1. Створення manifest агента

- **Запит або короткий зміст:** створити manifest спеціалізованого
  Build Engineer Agent для Java/Maven-проєкту.
- **Результат відповіді AI:** створено
  [build-engineer.agent.md](../.github/agents/build-engineer.agent.md) з
  описом агента та його робочого процесу.
- **Помилки та виправлення:** конкретні помилки в доступних матеріалах не
  зафіксовані.
- **Прийняте рішення:** використовувати окремий агент для послідовного
  створення, складання й перевірки проєкту.

## 2. Створення трьох Skills

- **Запит або короткий зміст:** додати три Skills для типових операцій
  агента.
- **Результат відповіді AI:** створено:
  [project-scaffold/SKILL.md](../.github/skills/project-scaffold/SKILL.md),
  [build-and-test/SKILL.md](../.github/skills/build-and-test/SKILL.md) і
  [github-actions/SKILL.md](../.github/skills/github-actions/SKILL.md).
- **Помилки та виправлення:** доступні матеріали не містять достовірного
  опису конкретних помилок цього етапу.
- **Прийняте рішення:** розділити підготовку структури, Maven
  build/test та CI на незалежні Skills.

## 3. Створення шести prompt-команд

- **Запит або короткий зміст:** створити набір команд для підготовки Git,
  проєкту, складання, Actions і перевірки.
- **Результат відповіді AI:** створено шість prompt-команд:
  [git-init.prompt.md](../.github/prompts/git-init.prompt.md),
  [create-project.prompt.md](../.github/prompts/create-project.prompt.md),
  [create-build.prompt.md](../.github/prompts/create-build.prompt.md),
  [create-actions.prompt.md](../.github/prompts/create-actions.prompt.md),
  [check.prompt.md](../.github/prompts/check.prompt.md) та
  [init.prompt.md](../.github/prompts/init.prompt.md).
- **Помилки та виправлення:** повний журнал помилок недоступний; відомо лише,
  що частину команд згодом уточнювали для безпечної повторної роботи
  (див. етап 8).
- **Прийняте рішення:** мати п’ять спеціалізованих команд і окремий
  оркестратор `init`.

## 4. Реалізація Java Maven-проєкту

- **Запит або короткий зміст:** реалізувати мінімальний Java-проєкт
  `HelloProject` з Maven, JUnit 5 та виконуваним JAR.
- **Результат відповіді AI:** створено Maven-конфігурацію, Java-класи,
  тести, batch/Unix CI-скрипти та документацію. У Git-історії цей етап
  зафіксовано комітом `Complete stage 4: implement and test project`.
- **Помилки та виправлення:** конкретні помилки під час реалізації у
  доступному журналі не зафіксовані. Зафіксовано успішне локальне складання
  та тести в артефактах Maven.
- **Прийняте рішення:** використовувати Java 17, JUnit 5, Maven і спільні
  скрипти `ci.bat`/`ci.sh` для локального та CI-запуску.

## 5. Налаштування GitHub Actions

- **Запит або короткий зміст:** налаштувати CI для перевірки Maven-проєкту на
  Windows, Ubuntu та macOS для `push` і `pull_request`.
- **Результат відповіді AI:** створено та оновлено
  [ci.yml](../.github/workflows/ci.yml), матрицю з
  `windows-latest`, `ubuntu-latest`, `macos-latest`, умови запуску
  відповідного скрипту та тригери для основних гілок. Git-історія містить
  коміт `Update GitHub Actions for stage 5`.
- **Помилки та виправлення:** підтверджених повідомлень про помилки немає.
  Під час етапу оновлено версії Actions і додано фільтри гілок.
- **Прийняте рішення:** на Windows запускати `ci.bat`, на Unix-подібних
  runner-ах — `ci.sh`; не приховувати помилки через `continue-on-error`.

## 6. Перевірка `push` і `pull_request` на Windows, Ubuntu та macOS

- **Запит або короткий зміст:** перевірити фактичні CI-прогони для обох
  подій на всіх трьох операційних системах.
- **Результат відповіді AI:** доступні дані GitHub Actions підтверджують
  успішні прогони:
  - `push` для коміту `Update GitHub Actions for stage 5`;
  - `pull_request` для тестового pull request;
  - у кожному з цих прогонів успішно завершилися job-и
    `windows-latest`, `ubuntu-latest` і `macos-latest`.
  Для Windows виконувався `ci.bat`, для Ubuntu та macOS — `ci.sh`.
- **Помилки та виправлення:** у підтверджених прогонах усі job-и завершилися
  успішно; окремих помилок, які потребували виправлення, не зафіксовано.
- **Прийняте рішення:** вважати матричну перевірку `push`/`pull_request`
  виконаною після успішного завершення всіх шести комбінацій.

## 7. Аудит етапу 6

- **Запит або короткий зміст:** перевірити коректність результатів CI етапу 6
  і використання команди перевірки.
- **Результат відповіді AI:** проведено окрему сесію аудиту, зафіксовану
  назвою `check command usage`; перевірено, що workflow має матрицю трьох
  ОС, події `push` і `pull_request`, а успішні job-и запускають правильний
  скрипт для своєї ОС.
- **Помилки та виправлення:** повний дослівний звіт аудиту та перелік
  знайдених проблем недоступні. У доступних матеріалах немає підтвердження
  додаткової помилки, виправленої саме під час аудиту.
- **Прийняте рішення:** залишити CI-структуру з матрицею та окремими
  платформними скриптами; не робити непідтверджених змін.

## 8. Виправлення prompt-команд для безпечного повторного запуску `init`

- **Запит або короткий зміст:** виправити ідемпотентність Build Engineer
  Agent, щоб повторний запуск `init` не дублював і не перезаписував наявні
  результати.
- **Результат відповіді AI:** у сесії з назвою `виправлення ідемпотентності
  Build Engineer Agent` оновлено п’ять prompt-команд. Зокрема, `init`
  тепер перевіряє наявний вміст перед дією, повторно не виконує `git init`,
  не перезаписує сумісні файли та розрізняє `REUSE`, `CREATE`, `UPDATE` і
  `SKIP`; `git-init` явно використовує наявний репозиторій.
- **Помилки та виправлення:** первинні prompt-команди не містили достатньо
  явних правил для безпечного повторного запуску. Точний текст помилки або
  конкретний небезпечний запуск не зберігся; виправленням стали перевірки
  наявного стану, мінімальні зміни та заборона destructive-дій.
- **Прийняте рішення:** повторний `init` має бути безпечним та
  ідемпотентним; за критичної помилки процес зупиняється без автоматичного
  повтору, а сумісні наявні результати перевикористовуються.
